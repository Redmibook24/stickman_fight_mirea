# Конфигурация эксперимента

Документ описывает, на чём и как были получены данные `docs/latency_samples.csv`,
чтобы прогон можно было повторить и получить сопоставимый результат.

## 1. Стенд

| Параметр            | Значение                                                   |
|---------------------|------------------------------------------------------------|
| Машина              | ноутбук, Intel Core Ultra 5 125H (14 ядер / 18 потоков), 15,4 ГБ ОЗУ |
| ОС                  | Windows 11 Pro 10.0.26200 (сборка 25H2)                    |
| Среда выполнения    | .NET SDK 9.0.203, конфигурация сборки Release              |
| Графики             | Python 3.12.6, matplotlib 3.9.2                            |
| Сеть                | локальная петля `127.0.0.1`, клиент и сервер на одной машине |
| Порт сервера        | 9060/UDP                                                    |
| Дата прогона        | 20.09.2026                                                  |

Клиент и сервер запускаются как два отдельных процесса. Внешняя сеть не задействована:
базовый RTT на петле — около 1 мс, всё, что выше, вносит эмулятор.

## 2. Параметры измерения

| Параметр                  | Значение | Где задаётся                          |
|---------------------------|---------:|---------------------------------------|
| Число PING в сценарии     | 50       | `--count 50`                          |
| Интервал между PING       | 300 мс   | `--interval 300`                      |
| Таймаут ответа            | 1000 мс  | `--timeout 1000`                      |
| Прогревочные PING         | 2        | `--warmup 2`                          |
| Зерно генератора эмулятора| 20250920 | `--seed 20250920`                     |

Интервал 300 мс лежит в требуемом диапазоне 200–1000 мс. Прогревочные пакеты отправляются
до начала измерений и **не попадают в журнал**: первый обмен в .NET заметно дороже остальных
из-за JIT-компиляции и ленивой инициализации сокета (без прогрева первый замер на петле
давал около 97 мс вместо 1 мс).

## 3. Эмуляция сетевых условий

Задание предлагает Clumsy. На этом стенде вместо внешнего эмулятора используется
**встроенный эмулятор в модуле `transport/`** (`EmulatedTransport`) — декоратор транспорта,
который применяет задержку, джиттер, потери и дубликаты к **исходящим датаграммам сервера**.

Причины выбора:

* эмулятор получает зерно (`--seed`), поэтому последовательность «потерять / задержать»
  повторяется от прогона к прогону — без этого сценарии с потерями невоспроизводимы;
* не нужны права администратора и установка стороннего драйвера;
* эмулятор покрыт модульными тестами (`tests/EmulatedTransportTests.cs`).

Ограничение: эмулятор работает на стороне сервера, поэтому заданная задержка добавляется
к RTT **один раз** (а не дважды, как было бы при симметричной эмуляции обоих направлений).
Кроме того, `Task.Delay` на Windows округляется до кванта системного таймера (~15,6 мс),
поэтому фактическая задержка получается на несколько миллисекунд больше заданной:
`delay=50` даёт медиану около 60 мс, `delay=100` — около 108 мс.

## 4. Сценарии

| Сценарий    | Параметры эмулятора       | Что проверяем                                  |
|-------------|---------------------------|------------------------------------------------|
| `baseline`  | нет                       | базовый RTT на петле                           |
| `delay_50`  | `delay=50`                | постоянная задержка 50 мс                      |
| `delay_100` | `delay=100`               | постоянная задержка 100 мс                     |
| `jitter`    | `delay=50,jitter=100`     | «плавающая» задержка 50–150 мс                 |
| `loss_5`    | `loss=5`                  | потеря 5 % ответов                             |
| `combined`  | `delay=100,loss=5`        | задержка 100 мс вместе с потерями 5 %          |

Дополнительно эмулятор умеет дублировать датаграммы (`duplicate=20`) — это нужно,
чтобы вручную проверить обработку `duplicate_response`; в шесть основных сценариев
этот режим не входит.

## 5. Как повторить прогон

```powershell
# из каталога Practice2_Latency
powershell -ExecutionPolicy Bypass -File tools/run_experiments.ps1
python tools/plot_latency.py
```

Скрипт собирает решение в Release, по очереди поднимает сервер с нужными параметрами
эмуляции, прогоняет клиента и перезаписывает `docs/latency_samples.csv`
(300 строк: 6 сценариев по 50 замеров). Второй командой строятся графики в `docs/graphs/`
и печатается сводная таблица, попадающая в `docs/Latency_Report.md`.

Отдельный сценарий можно прогнать вручную:

```powershell
# окно 1
server\bin\Release\net9.0\StickmanFight.Server.exe --port 9060 --emulate "delay=100,loss=5" --seed 20250920

# окно 2
client\bin\Release\net9.0\StickmanFight.Client.exe --port 9060 --experiment combined --count 50 --interval 300
```

## 6. Что влияет на воспроизводимость

* **Зерно эмулятора.** При одном и том же `--seed` номера потерянных пакетов совпадают:
  в прогоне ниже сценарии `loss_5` и `combined` потеряли одни и те же замеры (11, 33, 40).
* **Фоновая нагрузка машины.** Базовый RTT на петле — доли миллисекунды, поэтому редкие
  выбросы до 3–4 мс объясняются планировщиком ОС и сборкой мусора, а не сетью.
* **Квант системного таймера.** См. §3: он даёт систематическую добавку к заданной задержке.
* **Порт 9060 должен быть свободен.** Скрипт перед каждым сценарием снимает оставшиеся
  процессы сервера: иначе замеры уйдут к серверу от предыдущего сценария с чужими параметрами.
