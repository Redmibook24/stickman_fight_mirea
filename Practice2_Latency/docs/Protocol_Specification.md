# Протокол телеметрии PING/PONG, версия 1

Транспорт — **UDP**, порядок байт — **big-endian** (сетевой). Одна команда = одна датаграмма.
Разбор и сборка пакетов живут в модуле `protocol/` и не зависят ни от сокетов, ни от расчёта метрик.

## 1. Заголовок (7 байт)

| Смещение | Размер | Поле              | Тип      | Описание                              |
|---------:|-------:|-------------------|----------|---------------------------------------|
| 0        | 1      | `packetType`      | `uint8`  | тип пакета, см. §2                    |
| 1        | 2      | `sequenceNumber`  | `uint16` | порядковый номер пакета у отправителя |
| 3        | 2      | `payloadSize`     | `uint16` | размер полезной нагрузки в байтах     |
| 5        | 2      | `protocolVersion` | `uint16` | версия протокола, сейчас `1`          |

## 2. Типы пакетов

| Код | Имя        | Направление     | Размер пакета | Назначение                          |
|----:|------------|-----------------|--------------:|-------------------------------------|
| 1   | `PING`     | клиент → сервер | 15 байт       | замер задержки                      |
| 2   | `PONG`     | сервер → клиент | 31 байт       | ответ с отметками времени сервера   |
| 3   | `MOVEMENT` | клиент → сервер | —             | закреплён за практикой №1           |
| 4   | `SHOOT`    | клиент → сервер | —             | закреплён за практикой №1           |

## 3. Полезная нагрузка

### 3.1 `PING` — 8 байт

| Смещение | Размер | Поле                | Тип      | Описание                                    |
|---------:|-------:|---------------------|----------|---------------------------------------------|
| 7        | 8      | `clientSendTimeUs`  | `uint64` | время отправки по монотонным часам клиента, мкс |

### 3.2 `PONG` — 24 байта

| Смещение | Размер | Поле                   | Тип      | Описание                                        |
|---------:|-------:|------------------------|----------|-------------------------------------------------|
| 7        | 8      | `clientSendTimeUs`     | `uint64` | эхо отметки из `PING`                            |
| 15       | 8      | `serverReceiveTimeUs`  | `uint64` | момент приёма по монотонным часам сервера, мкс   |
| 23       | 8      | `serverSendTimeUs`     | `uint64` | момент отправки ответа, мкс                      |

Часы клиента и сервера не синхронизированы, поэтому **RTT считается только по часам клиента**:

```
RTT = t_получения_ответа(клиент) − t_отправки_PING(клиент)
```

Отметки сервера нужны, чтобы отделить время обработки на сервере
(`serverSendTimeUs − serverReceiveTimeUs`) от времени в сети; клиент печатает его рядом с RTT.
Эхо `clientSendTimeUs` дополнительно проверяется: если оно не совпадает с отправленным,
ответ отбрасывается как чужой или испорченный.

## 4. Проверка входных данных

Получатель проверяет датаграмму в таком порядке (`PacketCodec.TryParse*`):

1. длина не меньше заголовка — иначе `TooShort`;
2. `packetType` входит в перечисление — иначе `UnknownType`;
3. `protocolVersion` равен текущей версии — иначе `UnsupportedVersion`;
4. тип совпадает с ожидаемым (`PING` на сервере, `PONG` на клиенте) — иначе `UnexpectedType`;
5. `payloadSize` совпадает и с протоколом, и с фактической длиной — иначе `PayloadSizeMismatch`;
6. в датаграмме нет лишних байт после нагрузки — иначе `TrailingBytes`.

Ни одна проверка не читает данные за границами буфера: примитивы `BinaryCodec.TryRead*`
сдвигают курсор только при успехе. Все шесть ошибок покрыты тестами в `tests/PacketCodecTests.cs`.

## 5. Классификация ответов

Клиент хранит отправленные `PING` в таблице «в полёте» (`inFlight`) и по номеру пакета
относит каждый `PONG` к одной из категорий (`telemetry/LatencyTracker.cs`):

| Статус в журнале    | Когда назначается                                                |
|---------------------|------------------------------------------------------------------|
| `received`          | ответ пришёл раньше таймаута — RTT учитывается в статистике       |
| `timeout`           | ответа не было дольше таймаута (по умолчанию 1000 мс)             |
| `late_response`     | ответ пришёл позже таймаута — в RTT, SRTT и джиттер не идёт       |
| `duplicate_response`| ответ на уже закрытый `sequenceNumber`                            |
| `unknown_response`  | `sequenceNumber`, который клиент не отправлял                     |

Метрики считаются только по `received`:

```
SRTT = RTT                              для первого замера
SRTT = 0.875 * SRTT + 0.125 * RTT       для последующих
J    = (1 / (n − 1)) * Σ |RTT_i − RTT_(i−1)|
Loss = N_timeout / N_sent * 100 %
```

## 6. Журнал измерений

`docs/latency_samples.csv`, разделитель — `;`, дробная часть — через точку:

```
experiment_id;sample;sequence;sent_at_ms;rtt_ms;srtt_ms;status
baseline;1;1;0.526;4.172;4.172;received
loss_5;11;11;3088.499;;;timeout
```

Для `timeout`, `duplicate_response` и `unknown_response` поля `rtt_ms` и `srtt_ms` пустые.
Строки `unknown_response` пишутся с `sample = 0`, так как своего `PING` у них нет.
