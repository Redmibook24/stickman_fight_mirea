# Доказательства тестирования

Все логи сняты скриптами и лежат в [evidence/](evidence/). Сценарии 01-05 запускает
[`deploy/test_local.ps1`](../deploy/test_local.ps1) (сервер в Docker на ПК разработчика), сценарий 06
запускает [`deploy/test_vm.ps1`](../deploy/test_vm.ps1) (сервер в Docker на VM). Клиенты это
Windows-билд, запущенный с ключами автоматизации (см. README), так что каждый прогон воспроизводим.

В логах клиентов оставлены только строки сессии, Steam, транспорта и персонажей; лог сервера сохранён
целиком, кроме служебных строк Unity о памяти. Публичный IP и имя Steam-аккаунта заменены на `<скрыт>`.
SteamID `76561197960265728`, который Steam печатает при запуске сервера, это нулевой идентификатор-заглушка,
а не учётная запись.

## Пояснения к результатам

**Как отличается падение от штатной остановки.** При `kill -9` сервер не успевает ничего отправить,
и клиент узнаёт о разрыве по тайм-ауту транспорта: около 30 с в IP-профиле, около 20 с в Steam-профиле.
При `docker compose stop` сервер получает SIGTERM, закрывает соединения, и клиент видит
«сервер завершил работу» в ту же секунду.

**Повторный вход без перезапуска (сценарий 04).** Клиент запущен с ключом `-rejoin`: через 8 с после
входа он вызывает выход, снова ищет сессии и подключается. Сервер выдал ему новый id (1, затем 3),
потому что для сервера это новое подключение; процесс клиента тот же.

**Устаревшие подключения в логе сценария 05.** В начале сценария сервер показывает
«всего игроков: 3/4»: это клиенты сценария 04, закрытые аварийно. Сервер ещё не дождался их тайм-аута,
а затем был сам аварийно остановлен проверкой. Без этого он отключил бы их по тайм-ауту, как в сценарии 01
отключил закрытого клиента 1.

**Поиск через интернет на стенде без публичного IP.** Мастер-сервер Steam возвращает нашу сессию
(«сервер #0 из списка»), но перед показом клиент опрашивает сервер по его публичному IP. Пакет
из домашней сети на внешний адрес своего же роутера роутер не пропускает (NAT hairpin), поэтому
сессия помечена как не ответившая. Полный цикл проверен поиском в локальной сети: это тот же
`ISteamMatchmakingServers`, тот же ответ сервера и та же строка подключения.

**Маршрут Steam Sockets.** Во всех подключениях маршрут прямой, relay не используется. На клиенте это
адрес сервера в локальной сети, на сервере адрес шлюза Docker `172.18.0.1` или `192.168.56.1`:
контейнер видит клиента через NAT Docker.

**Служебные сообщения в логе сервера** (`steamclient.so: cannot open`, `S_API FAIL`, `flock ... errno = 13`)
разобраны в [Deployment.md](Deployment.md#8-служебные-сообщения-в-логе-запуска).
