# Спецификация протокола «Битва жердяев» v1

Транспорт — **UDP**. Одна команда = одна датаграмма, порядок байт — **little-endian**
(порядок хоста x86/ARM; преобразования выполняются явно через `BinaryPrimitives`,
поэтому протокол не зависит от платформы).

Датаграмма = заголовок (12 байт) + полезная нагрузка (0…65535 байт).
Реальный размер нагрузки в этой работе не превышает 22 байт, что заведомо меньше MTU,
поэтому фрагментации на уровне IP не происходит.

## 1. Заголовок пакета

| Смещение | Размер | Поле          | Тип        | Описание                                     |
|---------:|-------:|---------------|------------|----------------------------------------------|
| 0        | 1      | `Version`     | `uint8`    | версия протокола, сейчас `1`                 |
| 1        | 1      | `Type`        | `uint8`    | тип команды, см. §2                          |
| 2        | 2      | `Sequence`    | `uint16`   | порядковый номер пакета у отправителя        |
| 4        | 2      | `PayloadSize` | `uint16`   | размер полезной нагрузки в байтах            |
| 6        | 2      | `Reserved`    | `uint16`   | резерв (нули), выравнивание до 4 байт        |
| 8        | 4      | `Checksum`    | `uint32`   | CRC32 полезной нагрузки (полином `0xEDB88320`) |

Получатель обязан проверить в таком порядке: длину датаграммы → `Version` → соответствие
`PayloadSize` фактической длине → `Checksum`. Любое несовпадение — пакет отбрасывается
и пишется в лог (см. `ParseResult` в `Packet.cs`).

## 2. Типы команд (`PacketType`)

| Код | Имя           | Направление     | Нагрузка              | Смысл                               |
|----:|---------------|-----------------|-----------------------|-------------------------------------|
| 1   | `CONNECT`     | клиент → сервер | `ConnectPayload`      | рукопожатие, имя игрока             |
| 2   | `CONNECT_ACK` | сервер → клиент | `StatePayload`        | игрок принят, выдан id и состояние  |
| 3   | `DISCONNECT`  | клиент → сервер | пусто                 | корректный выход                    |
| 9   | `ERROR`       | сервер → клиент | UTF-8 текст           | пакет отвергнут, причина текстом    |
| 10  | `MOVEMENT`    | клиент → сервер | `MovementPayload`     | желаемое смещение за тик            |
| 11  | `SHOOT`       | клиент → сервер | `ShootPayload`        | выстрел                             |
| 20  | `STATE_UPDATE`| сервер → клиент | `StatePayload`        | обновлённое состояние игрока        |
| 21  | `SHOOT_RESULT`| сервер → клиент | `ShootResultPayload`  | результат выстрела                  |

Коды 12–16 зарезервированы под механики следующих практик: `MELEE_ATTACK`, `DASH`,
`GRAB`, `SHIELD`, `PICKUP_ITEM`.

## 3. Полезные нагрузки

### 3.1 `CONNECT` — `ConnectPayload` (1 + N байт)

| Смещение | Размер | Поле         | Тип      | Описание                        |
|---------:|-------:|--------------|----------|---------------------------------|
| 0        | 1      | `NameLength` | `uint8`  | длина имени в байтах, ≤ 32      |
| 1        | N      | `Name`       | UTF-8    | имя игрока                      |

### 3.2 `MOVEMENT` — `MovementPayload` (12 байт)

| Смещение | Размер | Поле | Тип     | Описание                      |
|---------:|-------:|------|---------|-------------------------------|
| 0        | 4      | `Dx` | `float` | смещение по X, метры          |
| 4        | 4      | `Dy` | `float` | смещение по Y (прыжок), метры |
| 8        | 4      | `Dz` | `float` | смещение по Z, метры          |

Клиент передаёт **желаемое смещение**, а не готовую позицию: позицию считает сервер.
Смещение по каждой оси обрезается до ±5 м, итоговая позиция — до ±50 м (границы арены).

### 3.3 `SHOOT` — `ShootPayload` (13 байт)

| Смещение | Размер | Поле       | Тип     | Описание                                   |
|---------:|-------:|------------|---------|--------------------------------------------|
| 0        | 1      | `WeaponId` | `uint8` | 1 — винтовка, 2 — гранатомёт, 3 — ближний бой |
| 1        | 4      | `DirX`     | `float` | направление выстрела, X                    |
| 5        | 4      | `DirY`     | `float` | направление выстрела, Y                    |
| 9        | 4      | `DirZ`     | `float` | направление выстрела, Z                    |

Урон по оружию: винтовка — 25, гранатомёт — 40, ближний бой — 15
(значения из README игрового проекта). Кулдаун между выстрелами — 200 мс.

### 3.4 `CONNECT_ACK` / `STATE_UPDATE` — `StatePayload` (22 байта)

| Смещение | Размер | Поле          | Тип      | Описание                                  |
|---------:|-------:|---------------|----------|-------------------------------------------|
| 0        | 2      | `PlayerId`    | `uint16` | идентификатор игрока, выданный сервером   |
| 2        | 4      | `X`           | `float`  | позиция по X                              |
| 6        | 4      | `Y`           | `float`  | позиция по Y                              |
| 10       | 4      | `Z`           | `float`  | позиция по Z                              |
| 14       | 2      | `Hp`          | `uint16` | здоровье, старт — 100                     |
| 16       | 2      | `Ammo`        | `uint16` | патроны, старт — 30                       |
| 18       | 2      | `AckSequence` | `uint16` | номер команды, на которую это ответ       |
| 20       | 2      | `Reserved`    | `uint16` | резерв (нули)                             |

### 3.5 `SHOOT_RESULT` — `ShootResultPayload` (10 байт)

| Смещение | Размер | Поле          | Тип      | Описание                           |
|---------:|-------:|---------------|----------|------------------------------------|
| 0        | 2      | `PlayerId`    | `uint16` | кто стрелял                        |
| 2        | 1      | `WeaponId`    | `uint8`  | из чего стрелял                    |
| 3        | 1      | `Hit`         | `uint8`  | 0 — промах, 1 — попадание          |
| 4        | 2      | `Damage`      | `uint16` | нанесённый урон                    |
| 6        | 2      | `AmmoLeft`    | `uint16` | остаток патронов                   |
| 8        | 2      | `AckSequence` | `uint16` | номер обработанной команды `SHOOT` |

### 3.6 `ERROR`

Полезная нагрузка — текст причины в UTF-8, без завершающего нуля.

## 4. Сценарий обмена

```
клиент                                   сервер
  |  CONNECT      seq=1  «Жердяй»          |   регистрирует игрока, пишет в лог
  | -------------------------------------> |
  |  CONNECT_ACK  id=1, поз., HP, патроны   |
  | <------------------------------------- |
  |                                        |
  |  MOVEMENT     seq=2  (dx, dy, dz)      |   проверяет CRC и seq, ограничивает шаг
  | -------------------------------------> |
  |  STATE_UPDATE ack=2, новая позиция     |
  | <------------------------------------- |
  |                                        |
  |  SHOOT        seq=3  (оружие, напр.)   |   проверяет кулдаун и патроны
  | -------------------------------------> |
  |  SHOOT_RESULT ack=3, попадание/урон    |
  | <------------------------------------- |
  |                                        |
  |  DISCONNECT   seq=N                    |   удаляет игрока из таблицы
  | -------------------------------------> |
```

## 5. Порядковые номера и надёжность

* `Sequence` — отдельный счётчик у клиента и у сервера, начинается с 1, растёт на каждый
  отправленный пакет, при переполнении `uint16` обнуляется.
* Сервер хранит номер последнего принятого пакета игрока. Пакет с `Sequence`
  не больше сохранённого считается дубликатом или «опоздавшим»: к состоянию он не применяется,
  в ответ уходит текущее `STATE_UPDATE`.
* Ответ сервера содержит `AckSequence` — это подтверждение конкретной команды.
* Повтор реализован только для рукопожатия (`CONNECT` — до 5 попыток по 1 с). Команды
  `MOVEMENT`/`SHOOT` не переотправляются: они устаревают быстрее, чем дойдёт повтор,
  — стандартный подход для потоковых игровых команд.

## 6. Ограничения текущей версии

* Сервер отвечает только тому клиенту, который прислал команду; рассылка состояния всех
  игроков (broadcast мира) появится в следующих практиках.
* Нет аутентификации и шифрования.
* HP уменьшается только у «условной цели»: попадание имитируется случайным образом,
  поскольку в практике №1 коллизии и другие игроки ещё не моделируются.
