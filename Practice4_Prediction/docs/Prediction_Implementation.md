# Client-Side Prediction и Server Reconciliation — реализация

## 1. Общие сведения

| Параметр | Значение |
|---|---|
| Проект | `prac4_multiplayer`: сетевой прототип с серверно-авторитетным перемещением |
| Команда | Пройдаков Дмитрий <br> Петров Артем <br> Бухальцев Павел |
| Движок | **Unity 6000.6.0f1** (URP). Методичка написана для Unreal Engine, работа выполнена на Unity: соответствие понятий приведено в разделе 3 |
| Сетевой стек | Netcode for GameObjects **2.13.3** (Unity Transport 2.6), Multiplayer Tools **2.2.12** (Network Simulator), Multiplayer Play Mode **2.0.2** |
| Хеш коммита для демонстрации | _`git rev-parse --short HEAD` → вставить сюда_ |

В Unity нет готового аналога `UCharacterMovementComponent` с предсказанием, поэтому весь механизм
(сохранённые ходы, отправка ввода, серверная проверка, коррекция и повторное проигрывание) написан
вручную по той же схеме, что и в Unreal. Это позволяет показать каждый шаг в коде.

## 2. Поток данных

```
 Клиент-владелец (Autonomous Proxy)                         Сервер (Listen Server / Host)
 ─────────────────────────────────                          ─────────────────────────────
 1. PlayerInputReader.BuildCmd(seq)  ─┐
    {seq, move(x,y), dash}            │
 2. MovementSim.Step(...)  ◄──────────┤  локальное предсказание:
    результат → SavedMove[seq]        │  персонаж двигается сразу
 3. SubmitInputsRpc(последние 6 cmd) ─┼──── unreliable ────►  4. Проверки: отправитель = владелец,
                                      │                          seq > lastProcessed, лимит частоты,
                                      │                          |move| ≤ 1, ValidateDash(...)
                                      │                       5. MovementSim.Step(...) — авторитетный
                                      │                          результат, transform сервера
 7. OwnerStateRpc(ackSeq, state) ◄────┼──── unreliable ─────  6. OwnerStateRpc → владельцу
    сравнить SavedMove[ackSeq] с state│                          ProxyStateRpc (20 Гц) → остальным
    ├─ совпадает → удалить ≤ ackSeq   │                          DashRejectedRpc → владельцу при отказе
    └─ расходится → перемотка к state │
       + повтор неподтверждённых cmd  │
 8. Визуальное сглаживание коррекции  │      Остальные клиенты (Simulated Proxy):
                                      │      интерполяция снимков с задержкой 100 мс
```

## 3. Роли компонентов (Unreal → Unity)

| Роль из методички | Класс в проекте | Ответственность |
|---|---|---|
| `GameMode` (только сервер) | [`GameRules`](../Assets/Prac4/Scripts/Runtime/GameRules.cs) | Одобрение подключений (`ConnectionApprovalCallback`), лимит игроков, создание персонажа и точка появления. Выполняется только на сервере |
| `PlayerController` | [`PlayerInputReader`](../Assets/Prac4/Scripts/Runtime/PlayerInputReader.cs) | Сбор локального ввода у владельца. Нажатие рывка запоминается до ближайшего тика симуляции. Формирует `InputCmd`, то есть намерение игрока, а не координаты |
| `ACharacter` | [`PlayerCharacter`](../Assets/Prac4/Scripts/Runtime/PlayerCharacter.cs) + `CharacterController` + `NetworkObject` | Персонаж: модель, цвет (свой / чужой / рывок), камера владельца, маркер последней подтверждённой сервером позиции |
| `UCharacterMovementComponent` | [`PredictedMovement`](../Assets/Prac4/Scripts/Runtime/PredictedMovement.cs) + [`MovementSim`](../Assets/Prac4/Scripts/Runtime/MovementSim.cs) | Фиксированный шаг 50 Гц, Saved Moves, отправка ввода, серверная проверка, коррекция, повторное проигрывание, интерполяция Simulated Proxy |
| Network Emulation | `NetworkSimulator` (Multiplayer Tools) + [`NetLabHud.ApplyProfile`](../Assets/Prac4/Scripts/Runtime/NetLabHud.cs#L42) | Задержка, джиттер и потери пакетов на уровне транспорта UTP |

Роли экземпляров персонажа (видны в подписи над персонажем):

* **Autonomous Proxy**: свой персонаж на клиенте. Управляется локально с предсказанием.
* **Серверная копия**: авторитетное состояние чужого персонажа на сервере.
* **Simulated Proxy**: чужой персонаж на клиенте. Отображается по снимкам сервера с интерполяцией.
* **Хост**: свой персонаж хоста. Он одновременно сервер и владелец, поэтому предсказание ему не нужно.

`MovementSim.Step` — общий детерминированный шаг движения. Его вызывают и сервер (как авторитет), и клиент
(для предсказания и для повторного проигрывания ввода). Поэтому при одинаковом вводе результаты совпадают,
и коррекции возникают только при настоящем расхождении.

## 4. Выбранное действие: рывок (dash) с кулдауном

* Длительность 10 шагов (0,2 с), скорость 22 м/с, направление совпадает с текущим направлением взгляда.
* Повторное использование не раньше чем через 75 шагов (1,5 с).

**Серверные проверки** ([`MovementSim.ValidateDash`](../Assets/Prac4/Scripts/Runtime/MovementSim.cs#L58), [`ServerApply`](../Assets/Prac4/Scripts/Runtime/PredictedMovement.cs#L333), [`SubmitInputsRpc`](../Assets/Prac4/Scripts/Runtime/PredictedMovement.cs#L301)):

| Проверка | Что делает сервер при нарушении |
|---|---|
| RPC пришёл от владельца объекта (`InvokePermission = Owner` + сравнение `SenderClientId`) | Игнорирует пакет |
| Порядковый номер `seq` больше последнего обработанного | Дубликаты и устаревшие команды пропускаются |
| Частота ввода не выше 50 команд/с (token bucket, запас 10) | Лишние команды отбрасываются: защита от speed hack через частые пакеты |
| Длина вектора движения не больше 1 | Вектор обрезается, событие пишется в журнал |
| Рывок не выполняется прямо сейчас | `RejectedAlreadyDashing` |
| Кулдаун истёк (`CooldownTicksLeft == 0`) | `RejectedCooldown` |
| Персонаж на земле (`IsGrounded`) | `RejectedNotGrounded` |
| Столкновения | Сервер сам двигает `CharacterController`, стены и препятствия учитываются на сервере |

При отказе сервер не начинает рывок, отправляет владельцу `DashRejectedRpc`, и в следующем
`OwnerStateRpc` клиент получает авторитетное состояние без рывка.

## 5. Сравнение: без локального предсказания и с ним

Режимы переключаются на клиенте клавишами **1** (предсказание рывка) и **2** (предсказание движения).

| | Без предсказания (клавиша 1 → ВЫКЛ) | С предсказанием (по умолчанию) |
|---|---|---|
| Что делает клиент при нажатии | Отправляет `dash = true` и не запускает рывок локально (`AllowDashStart = false`) | Сразу проверяет условия локально и начинает рывок |
| Когда персонаж начинает рывок | Когда приходит `OwnerStateRpc`, где сервер уже выполнил рывок. Тогда же срабатывает коррекция «состояние рывка» | В том же тике, что и нажатие |
| Задержка «нажатие → рывок» (HUD и журнал) | ≈ RTT + время до тика. Ожидаемо ~200+ мс при профиле 100 мс | ≈ 0–20 мс (один тик) |
| Авторитетность | Сервер | Сервер: результат клиента всё равно сверяется с сервером |

Аналогично с клавишей **2** (без предсказания движения) персонаж стоит на месте, пока не придёт
подтверждение сервера, и двигается рывками в такт пакетам.

## 6. Случай расхождения и серверная коррекция

Способы намеренно вызвать расхождение:

1. **C — «клиент игнорирует кулдаун»**. Клиент предсказывает рывок до окончания кулдауна, сервер его
   отклоняет (`RejectedCooldown`). Клиент получает состояние без рывка, видит расхождение по позиции и рывку,
   перематывается к позиции сервера и повторно применяет неподтверждённые вводы.
   В журнале: `СЕРВЕР ОТКЛОНИЛ рывок … кулдаун не истёк` и `[КОРРЕКЦИЯ] … (состояние рывка)`.
2. **X — «клиент ускоряет себя ×1.8»**. Клиент двигается быстрее и отправляет вектор длиной 1.8. Сервер
   обрезает его до 1, клиент постоянно получает коррекции и «откатывается» к серверной позиции (синий диск).
3. **Рывок у препятствия `DashWall`**. При задержке и потерях стена и другие игроки дают небольшие расхождения,
   которые исправляются коррекцией.
4. **Рывок в воздухе**. Если сойти с платформы `Platform` и нажать рывок, сервер отклонит его (`RejectedNotGrounded`).

Во всех случаях соединение не рвётся. Коррекция мгновенно исправляет корневой объект, а модель (`Visual`)
плавно догоняет его за ~0,1–0,2 с (сглаживание), поэтому телепортации не видно. Прыжки больше 3 м
применяются сразу.

## 7. Эмуляция сети

Используется `NetworkSimulator` из Multiplayer Tools. `UnityTransport.SetDebugSimulatorParameters` в NGO 2.x
помечен устаревшим и ничего не делает. Профили переключаются в HUD **на клиенте**:

| Клавиша | Профиль | Параметры |
|---|---|---|
| F1 | T1 | `PacketDelay = 0, Jitter = 0, Loss = 0%` |
| F2 | T2/T3 | `PacketDelay = 100 мс, Jitter = 0, Loss = 0%` |
| F3 | T4/T5 | `PacketDelay = 175 мс, Jitter = 25 мс, Loss = 4%` |

Симулятор работает в редакторе и в Development Build. Фактический RTT выводится в HUD
(`RTT транспорта` и `ввод→подтверждение`).

## 9. Известные ограничения

* Снимки Simulated Proxy интерполируются по локальному времени получения, а не по серверному тику,
  поэтому при сильном джиттере чужие персонажи двигаются менее плавно.
* Нет компенсации задержки (lag compensation) для взаимодействия игроков. Столкновения с чужим персонажем
  на клиенте считаются по его интерполированной (прошлой) позиции, что может давать небольшие коррекции.
* Если все копии ввода потеряны, сервер пропускает эти шаги, а клиент получает коррекцию. Сервер не
  экстраполирует ввод.
* Клиент и сервер используют одинаковый код на `float`. Между разными платформами возможны микрорасхождения,
  для них предусмотрен порог коррекции 5 см.
* Хост — одновременно сервер, поэтому у его персонажа нет задержки. Эксперимент проводится на клиенте.
